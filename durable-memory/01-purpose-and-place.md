# Purpose and place

## Purpose

`lmcad` is a native host for lmscript `_dsl_` bytecode that builds 3D scenes and renders still images. The first milestone should prove the complete small path: a compiled `.dslb` file, the exact JSON schema used to compile it, the embedded C++ VM, host-side scene objects, and a headless PNG output. Later milestones can add mesh exports, animation and video frames without changing that basic host boundary.

The CLI owns the process, renderer, scene lifetime, file access and command-line interface. A DSL chunk only invokes operations made available by the selected schema. It should not be treated as a serialized scene format: it is a sequence of instructions that calls host functions and methods.

## Place in the framework

- **lmscript** is the authoring compiler. It compiles a `_dsl_` block against a JSON schema into portable bytecode. The schema describes context names, types, function and method signatures; the compiler uses it to type-check names and calls.
- **cpp-dsl-sdk** is the C++ runtime implementation. `include/dslvm.hpp` provides the loader, verifier, host registry and VM as a C++17 header with no non-standard-library dependency. Hosts vendor the exact header and pin its commit and hash in `sdk.lock`.
- **lmor-dsl** is the reference host pattern. One CLI embeds the SDK, binds schema objects to the real C++ library, accepts a bytecode file plus schema, and keeps examples, tests and durable implementation notes in the host repo. Its OR-Tools dependency is specific to that application; lmcad should not inherit it.
- **lmcad** follows the host pattern with a geometry and raster backend. It owns `Scene`, `Shape`, camera, material and light objects and maps schema calls to native operations. It should keep schema and implementation small and explicit so that lmscript remains the authoring layer and the VM remains generic.

The cross-language bytecode rules belong to the language spec; SDK implementations are expected to agree through shared conformance vectors. lmcad must use the compiler-generated bytecode and the vendored SDK rather than adding private bytecode behavior. The language and bytecode specification files referenced by the existing repos were not present in the searched local checkouts or installed npm package on this machine; their locations are recorded in the investigation report for the operator.

## Scope boundary

The first vertical slice is one scene, a few primitive meshes, a camera, a light, a material, and one deterministic PNG render. Scene construction and rendering happen in one process. Input data, if later needed, comes through ordinary host-registered functions, not special VM behavior. Animation can be added after the language supports bounded iteration and collection values.
